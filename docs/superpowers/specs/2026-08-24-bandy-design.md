# Bandy — дизайн 3D-игры от первого лица

Дата: 2026-08-24
Статус: утверждён, готов к составлению плана реализации

## 1. Что делаем

Браузерная 3D-игра от первого лица. Игрок оказывается в комплексе комнат,
соединённых дверями и коридорами. Он ходит, подбирает предметы, кладёт их в
инвентарь, берёт в руки и применяет один предмет на другой — например, ключ на
висящий на двери замок. Цель — найти дверь с надписью EXIT, открыть её и пройти
по длинному коридору к белому свету в конце.

Референс по духу и ощущению — Hello Neighbor. Антагониста при этом нет: угрозы,
преследования, стелса и проигрыша в игре не предусмотрено. Это исследовательская
головоломка, а не хоррор про побег от врага.

Обязательное требование: играбельность и на десктопе (мышь + WASD), и на телефоне
(тач). Мобильная версия — не порт «потом», а вторая реализация того же интерфейса
ввода, заложенная в архитектуру с самого начала.

## 3. Ограничения среды

Эти ограничения не обсуждаются и влияют на решения ниже.

**GitHub Pages не отдаёт кастомные HTTP-заголовки.** Значит нет `COOP`/`COEP`,
значит нет `SharedArrayBuffer`. Всё, что требует потоков — включая Unity WebGL и
многопоточный экспорт Godot — использовать нельзя. Это одна из причин выбора
Three.js.

**`vite.config.ts` обязан содержать `base: '/bandy/'`.** Сайт живёт в подпапке, а
не в корне домена. Без этого — белый экран и 404 на все ресурсы.

**ES-модули не работают по `file://`.** Открывать игру локально можно только через
dev-сервер.

**На iPhone Safari нет Fullscreen API.** Ландшафтную ориентацию залочить нельзя,
адресная строка съедает экран. Обход — PWA-манифест и добавление на главный экран.

**Pointer Lock и hover не существуют на мобильных.** Подсветка цели работает через
центральный прицел, а не через положение курсора.

**Мобильные GPU плохо переносят realtime-тени и большое число draw call'ов.**

## 4. Архитектура

Проект делится на слои с жёсткой границей. Главное правило:

> **`src/core/` не импортирует three.js. Никогда.**

- **`core/`** — чистый TypeScript. Типы и валидация уровня, состояние мира,
  инвентарь, реестр взаимодействий, генерация коллайдеров, математика коллизий.
  Запускается и тестируется без браузера и WebGL.
- **`render/`** — three.js. Строит сцену из уровня, анимирует двери, рисует предмет
  в руках. Читает состояние из `core`, отправляет туда команды, подписывается на
  события.
- **`input/`** — прячет разницу между «pointer lock + WASD» и «стик + свайп» за
  единым интерфейсом. Остальной код не знает, с какого устройства играют.
- **`ui/`** — HUD и инвентарь как DOM-оверлей, не 3D. Это бесплатно даёт тач-скролл,
  нормальные шрифты, кнопки нужного размера под палец и ноль лишних draw call'ов.

Отвергнутые варианты: ECS (избыточен для трёх комнат и пяти предметов) и логика
прямо на графе сцены three.js (нетестируемо, срастается с рендером).

### Дерево проекта

```
src/
  main.ts              точка входа, игровой цикл
  config.ts            размеры, скорости, константы

  core/                чистый TS, ноль three.js, покрыт тестами
    types.ts           Level, Room, Door, ItemDef, WorldState
    validate.ts        JSON -> Level | ошибки
    colliders.ts       Level -> AABB[]
    collision.ts       разрешение движения, чистые функции
    world.ts           состояние мира, команды, события
    inventory.ts
    interactions.ts    реестр «предмет на предмет»

  render/
    scene.ts           Level -> сцена
    walls.ts           стены с проёмами
    doors.ts           анимация открывания
    hand.ts            предмет в руках, вторая камера
    sign.ts            EXIT через canvas-текстуру

  input/
    index.ts           общий InputState
    desktop.ts         pointer lock + WASD
    touch.ts           стик + свайп + кнопки

  ui/
    hud.ts             прицел, подсказка взаимодействия
    inventory.ts       DOM-оверлей

  levels/
    level_01.json
```

Тесты лежат рядом с кодом как `*.test.ts` и существуют только в `core/`.

## 5. Формат уровня

### Единицы и размеры

Метры, сетка 1 м. Игрок: рост 1.7, глаза на 1.6, радиус 0.3. Комнаты высотой 3.0,
стены толщиной 0.2, дверной проём 0.9 × 2.1. Все значения — константы в
`src/config.ts`.

Толщина 0.2 — это стена ОДНОЙ комнаты: она строится внутрь от границы `rect`
целиком, а не растягивается по обе стороны от неё (сознательный выбор против
z-fighting на стыке, см. `colliders.ts`). На стыке двух комнат это даёт суммарно
0.4 м, и внутренний размер комнаты по каждой стороне со стеной оказывается на 0.2 м
меньше, чем в `rect`. Автору карты считать проходы и дверные проёмы нужно с учётом
этого вычета, а не по номинальным 0.2.

### Коридор не является отдельной сущностью

Геометрически коридор — это узкая длинная комната. Второй тип сущности означал бы
дублирование генерации стен, коллизий и освещения без всякой выгоды. В формате есть
только `room`; коридор — это `room` с малой шириной. Финальный коридор за дверью
EXIT — такая же комната с триггером победы в дальнем конце.

### Схема

```json
{
  "id": "level_01",
  "spawn": { "room": "hall", "x": 2, "z": 2, "yaw": 0 },

  "rooms": [
    { "id": "hall",       "rect": [0, 0, 8, 6],  "color": "#8b8b8f", "light": 0.9 },
    { "id": "corridor_a", "rect": [8, 2, 6, 2],  "color": "#6f6f74", "light": 0.6 },
    { "id": "office",     "rect": [14, 0, 6, 6], "color": "#7d8288", "light": 0.9 },
    { "id": "exit_hall",  "rect": [14, 6, 3, 20],"color": "#5a5a60", "light": 0.4 }
  ],

  "doors": [
    { "id": "d_hall_corr",   "between": ["hall", "corridor_a"],   "at": [8, 3] },
    { "id": "d_corr_office", "between": ["corridor_a", "office"], "at": [14, 3],
      "lock": "lock_front" },
    { "id": "d_exit",        "between": ["office", "exit_hall"],  "at": [15.5, 6],
      "sign": "EXIT" }
  ],

  "locks": {
    "lock_front": "Латунный замок"
  },

  "items": [
    { "def": "key_brass", "room": "hall", "at": [6, 0.9, 4.5] }
  ],

  "triggers": [
    { "id": "win", "room": "exit_hall", "rect": [14, 24, 3, 2], "effect": "win" }
  ],

  "interactions": [
    { "use": "key_brass", "on": "lock_front",
      "effects": [
        { "destroy": "lock_front" },
        { "consume": "key_brass" },
        { "say": "Замок щёлкнул и упал на пол." }
      ] }
  ]
}
```

`rect` — это `[x, z, ширина, глубина]`.

`at` у двери — точка на общей стене двух комнат. Сторона и ориентация выводятся
автоматически из того, какие комнаты дверь соединяет. Это снимает с автора карты
необходимость указывать `facing` — поле, в котором ошибиться легче всего.

### Где что лежит

Определения предметов (`ItemDef`: идентификатор, отображаемое имя, можно ли брать в
руки) живут в общем файле `src/levels/items.json` — предметы переиспользуются между
уровнями. Поле `def` у записи в `items` ссылается именно туда.

Правила взаимодействий лежат **внутри файла уровня**, в секции `interactions`, потому
что «этот ключ открывает этот замок» — свойство конкретной карты, а не предмета.

Замок создаётся из поля `lock` у двери; идентификатор задаёт автор карты, а положение
и размер выводятся из положения двери. Замок **глубже полотна и центрирован на нём**,
поэтому виден и доступен прицелу из обеих смежных комнат. Ранняя редакция вешала его
на одну грань, со стороны первой комнаты в `between`; это делало непроходимым любой
уровень, где к запертой двери подходят с другой стороны, — уровень при этом проходил
и валидацию, и сквозной тест ядра (§12).

Единственное собственное свойство замка — **название**, и оно живёт в блоке `locks`
файла уровня: отображение «идентификатор → строка». Замок сам себя описывает
(«Железный замок»), но никогда не называет нужный ключ. Названия предметов в этой
игре и есть их типы, поэтому информация у игрока та же — но сопоставляет её он, а не
игра. Иначе головоломку, где сопоставление не тривиально, нельзя будет построить
никогда, потому что HUD печатал бы ответ прямо из реестра взаимодействий.

Отображение плоское, а не запись с полями: у замка ровно одно свойство. Понадобится
второе — тогда и вырастет.

### Прочие поля

`light` — яркость освещения комнаты. В v1 это множитель ровного света. Когда
появятся полумрак и фонарик, смысл поля сохранится и карту переписывать не
придётся.

### Генерация геометрии

Стены строятся по периметру каждой комнаты. Стена с дверью режется не CSG, а тремя
прямоугольниками: слева от проёма, справа и перемычка сверху. Просто, быстро, не
ломается на стыках.

Коллайдеры генерируются из тех же данных отдельной чистой функцией
`buildColliders(level) -> AABB[]`. Закрытая дверь добавляет свой коллайдер,
открытая — убирает.

### Валидация

Карта пишется руками, поэтому опечатки неизбежны, а проявляются они как тихие баги,
которые ловятся получасом хождения по лабиринту. `validateLevel(json)` возвращает
либо готовый `Level`, либо список внятных ошибок, и при ошибке игра показывает их
вместо запуска.

Что обязана ловить валидация:

- дверь ссылается на несуществующую комнату;
- точка двери не лежит на общей стене указанных комнат, и вокруг неё не хватает
  места на проём шириной `DOOR.width` (иначе проём режется за пределами стыка);
- комнаты пересекаются;
- предмет расположен вне своей комнаты;
- замок висит на двери, но ни одно правило взаимодействия его не открывает;
- у замка нет записи в `locks`, либо запись в `locks` не использована ни одной
  дверью — и то и другое означает опечатку в идентификаторе;
- триггер лежит вне своей комнаты;
- точка появления игрока вне своей комнаты;
- один и тот же идентификатор занят двумя разными сущностями (предметом, дверью,
  замком или триггером) — иначе он молча разрешится по порядку приоритетов
  внутри `classify()`;
- уровень непроходим от точки появления: победа (триггер или правило с эффектом
  `win`) недостижима перебором «какие комнаты доступны → какие предметы в них
  собраны → какие двери эти предметы открывают» до неподвижной точки. Отдельно
  называется самая частая опечатка автора карты — нужный ключ лежит в комнате,
  куда нельзя попасть, не открыв замок, который этот же ключ отпирает;
- поля JSON не той формы или не того типа (мусор в `color`/`light`, `rect` не из
  четырёх чисел и т.п.) — эта проверка идёт раньше проверок смысла, чтобы ошибка
  называла настоящую причину, а не выглядела как опечатка в другом поле.

Валидатор пишется руками, без `zod`: ноль зависимостей, формулировки ошибок на
нашем языке, покрытие тестами тривиально.

## 6. Ядро: предметы, инвентарь, взаимодействия

### Расположение предмета

```ts
type ItemLocation =
  | { kind: 'world'; room: string; at: Vec3 }
  | { kind: 'inventory' }
  | { kind: 'hand' }
  | { kind: 'gone' }
```

Одно поле вместо набора флагов. Предмет не может находиться в двух местах
одновременно — это гарантирует тип, а не дисциплина. Рендер смотрит на `kind` и
решает, что рисовать.

### Замок — объект, а не флаг

У двери есть поле `lock`. Дверь заперта ровно до тех пор, пока объект замка
существует в мире. Отдельного состояния «заперта/отперта» нет.

Это убирает класс багов, где флаг и объект рассинхронизировались, и убирает из
системы эффект `unlock` — достаточно `destroy`. Кроме того, замок становится
самостоятельной целью прицела: игрок наводится на висящий замок, а не на дверь.

### Реестр взаимодействий

Правило — тройка «что применили», «на что», «что произошло»:

```json
[
  { "use": "key_brass", "on": "lock_front",
    "effects": [
      { "destroy": "lock_front" },
      { "consume": "key_brass" },
      { "say": "Замок щёлкнул и упал на пол." }
    ] }
]
```

Хардкод вида `if (item === 'key' && target === 'lock')` запрещён. Добавление
предмета должно быть правкой данных, а не кода.

Полный список эффектов, намеренно короткий: `take`, `consume`, `destroy`,
`toggleDoor`, `setFlag`, `say`, `win`.

`toggleDoor` добавлен при составлении плана: шести перечисленных эффектов не хватало,
чтобы выразить открывание двери, а это основное действие игры. Само правило
«незапертая дверь открывается» по-прежнему живёт в коде, а не в реестре — эффект нужен
лишь для того, чтобы результат разрешения был однородным списком эффектов.

Для всей первой версии реестр содержит одну запись. Подобрать предмет и открыть
незапертую дверь — это не контент, а правила игры, и они живут в коде.

### Поведение по умолчанию

Когда правила в реестре нет, срабатывает поведение по типу цели:

| Цель | В руках | Результат |
|---|---|---|
| предмет на полу | что угодно | подобрать в инвентарь |
| незапертая дверь | что угодно | открыть / закрыть |
| запертая дверь | что угодно | «Заперто. На двери висит замок.» |
| замок | ничего | «Железный замок. Нужно чем-то открыть.» |
| замок | неподходящий предмет | «Обрезок трубы сюда не подходит.» |
| триггер выхода | — | победа |

Отказ всегда сопровождается внятной причиной в HUD. Без этого в лабиринте
начинается слепое тыканье во всё подряд.

### Подсказка и действие — один код

```
прицел -> targetId
world.resolve(targetId, held, 'describe') -> { prompt } | { refusal }
                                              игрок нажал
world.resolve(targetId, held, 'apply')    -> Effect[] -> события
```

`describe` и `apply` — один и тот же код разрешения, вызванный в двух режимах.
Отсюда следует инвариант: подсказка не может соврать. Ситуация «HUD пишет
"Открыть", жмёшь — ничего не происходит» невозможна по построению. Если развести их
на две функции, они разъедутся — это происходит всегда.

**Уточнение от 26 августа 2026: отказ показывается после первой попытки.**

Инвариант выше относится к **решению**, а не к его формулировке. Изначальная
редакция не различала эти два, и из неё следовало, что причину отказа надо
показывать сразу при наведении прицела. На практике это выдавало загадку до того,
как игрок к ней подошёл: достаточно было мазнуть прицелом по двери в конце
коридора, чтобы узнать, что она заперта.

Поэтому у ветки `ok: false` появляется необязательное поле `untried` — что
показывать, пока игрок не нажимал на эту цель ни разу:

| шаг | что видит игрок |
|---|---|
| навёл прицел | «Открыть дверь» |
| нажал действие | «Заперто. На двери висит замок.» |
| навёл снова | «Заперто. На двери висит замок.» |

Разрешение по-прежнему одно: `resolveInteraction` считает `ok`, эффекты, отказ и
`untried` за один проход и ничего не знает о том, что игрок уже пробовал. Знание
игрока — состояние **мира**: `World` ведёт множество целей, на которые нажимали, и
`describe` убирает `untried` из ответа, как только цель попробовали. `interact`
отмечает попытку.

Соврать это может ровно один раз на цель, и ровно тем способом, который в игре
такого рода и есть содержание: нажал — не открылось. Со второго взгляда HUD
говорит правду и продолжает говорить её всегда. Вариант «всегда показывать
"Открыть дверь", а отказ выдавать только по нажатию» отвергнут: он врёт
неограниченно долго, и игрок выучивает, что HUD-у верить нельзя.

`untried` заводится только там, где скрытая причина создаёт интригу — то есть у
запертой двери, и больше нигде. Замок `untried` не получает **никогда**, и это не
недоделка, а вторая половина той же мысли:

- **дверь** скрывает, что заперта, пока её не попробовали: загадка не должна быть
  видна с другого конца коридора;
- **замок** читается целиком, как только на него навёлся: игрок стоит перед ним и
  видит его глазами, включая материал.

Отсюда следует, что и отказ «этот предмет сюда не подходит» показывается сразу, до
попытки, — и это не спойлер, а та же читаемость: видно железный замок, видно обрезок
трубы, и без подсказки ясно, что одно к другому не подойдёт. Прятать это значило бы
делать игру глупее, а не интереснее.

Эффекты применяются к состоянию и порождают события (`itemTaken`,
`objectDestroyed`, `doorOpened`, `won`). На события подписаны рендер и HUD. Ядро
ничего не знает ни про анимацию, ни про звук.

### Инвентарь

Плоский список идентификаторов. Без веса, без стеков, без сетки ячеек, без лимита.

Открывается по `KeyI`, `Tab` или кнопке на мобиле. **При открытом инвентаре игра
встаёт на паузу**: движение и взгляд отключаются, pointer lock отпускается. Для
головоломки это нормально, а на телефоне это единственный вменяемый вариант —
иначе свайп по списку крутил бы камеру.

Выбор предмета переводит его в `hand`. Предмет в руках ровно один. Повторный выбор
того же предмета возвращает его в инвентарь.

Рисуется DOM-оверлеем: список крупных строк с названиями. Иконок в v1 нет.

## 7. Движение и коллизии

Пол плоский, потолок ровный, гравитации, прыжков и ступенек нет. Поэтому игрок —
это круг радиуса 0.3 в плоскости XZ, а стены — прямоугольники в той же плоскости.
Задача сводится к двумерной.

Разрешение движения — раздельно по осям: смещаемся по X, откатываем при
пересечении, затем смещаемся по Z, откатываем при пересечении. Это бесплатно даёт
естественное скольжение вдоль стены.

Sweep-проверка не нужна. Она защищает от туннелирования на больших скоростях, а при
скорости 3 м/с и кадре 16 мс смещение составляет 5 см при радиусе 30 см.

Но есть мобильная дыра: после сворачивания вкладки `deltaTime` приходит равным
нескольким секундам, и игрок телепортируется сквозь полкарты. Поэтому **dt всегда
клампится** потолком около 50 мс, а `visibilitychange` ставит игру на паузу.

Скорость ходьбы — около 3 м/с. Спринта в v1 нет.

Взгляд: `mousemove` в режиме pointer lock даёт дельту, она идёт в yaw и pitch. Pitch
ограничен ±85°. Pointer Lock требует жеста пользователя, поэтому первый экран —
«Нажми, чтобы начать». `Escape` отпускает lock и открывает паузу.

## 8. Ввод

```ts
interface InputState {
  move:            { x: number; y: number }   // -1..1, желаемое направление
  look:            { dx: number; dy: number } // дельта за кадр
  interact:        boolean                     // фронт нажатия
  toggleInventory: boolean
}
```

Игровой цикл видит только это. Именно эта граница делает мобильную версию второй
реализацией интерфейса, а не отдельным проектом.

Активная схема определяется **не по user agent** (он врёт), а по факту событий:
пришло touch-событие — включается тач-UI, пришёл mousemove или pointer lock —
десктопный. На ноутбуке с тачскрином работают обе, переключаясь на лету.

### Тач-схема

Левая половина экрана — плавающий виртуальный стик: появляется там, где палец
коснулся, а не в фиксированном углу. В фиксированный стик нужно попадать вслепую.

Правая половина — свайп для поворота камеры, без инерции. Инерция мешает точно
навестись на мелкую цель вроде замка.

Кнопка «Взять» справа внизу, кнопка инвентаря справа сверху. Размер минимум 48 CSS-
пикселей, целевой — 64.

Две ловушки, на которых ломается большинство самодельных тач-контролов:

1. **Обязательно отслеживать `pointerId`.** Иначе второй палец (поворот камеры)
   перехватит события первого (стик), и управление начнёт залипать. Каждый активный
   палец — отдельная запись со своим id.
2. **`touch-action: none` на канвасе и `preventDefault`.** Иначе браузер решит, что
   свайп это скролл, а два пальца это зум, и страница поедет вместе с игрой.

### Мобильные ограничения и обходы

| Проблема | Решение |
|---|---|
| На iPhone нет Fullscreen API | PWA-манифест плюс `apple-mobile-web-app-capable` |
| Ландшафт не залочить без fullscreen | В портрете оверлей «Поверни телефон» |
| `100vh` врёт из-за адресной строки | Везде `100dvh` |
| Кнопки лезут под чёлку и home-индикатор | `viewport-fit=cover` и `env(safe-area-inset-*)` |
| `devicePixelRatio` = 3 убивает fps | `setPixelRatio(Math.min(dpr, 2))`, на слабых 1.5 |
| Уход в фон ломает время кадра | `visibilitychange` -> пауза, dt клампится |

## 9. Взаимодействие и HUD

Raycast из центра камеры на 2.5 м каждый кадр. Объектов десятки, стоимость
пренебрежима. Попадание в интерактивный объект даёт `targetId`, дальше работает
схема `describe` / `apply`.

Цель подсвечивается поднятием emissive. Под прицелом выводится строка подсказки. На
мобиле логика та же, отличается только то, чем игрок нажимает: кнопка «Взять»
становится активной.

Предмет в руках рисуется в правом нижнем углу отдельной камерой с малым near-plane —
иначе он протыкает стены при подходе вплотную.

В HUD больше ничего нет. Полоски здоровья нет, потому что умирать не от чего.
Миникарты нет, потому что в лабиринте она убивает основную механику.

### Двери

Открываются поворотом вокруг петли примерно за 0.4 секунды с плавным замедлением.
Дверь всегда распахивается в сторону от игрока — так она не бьёт по лицу и не
выталкивает его.

Коллайдер двери не анимируется: снимается в момент начала открытия и возвращается в
конце закрытия. Анимированный коллайдер способен зажать игрока в проёме, а выигрыш
от него нулевой.

## 10. Рендер

Текстурных файлов нет. Читаемость пространства обеспечивают пять приёмов, ни один из
которых не требует ассетов:

1. **Цвет на комнату** из JSON. Игрок запоминает «синеватая комната» вместо «одна из
   шести серых».
2. **Разная светлота пола, стен и потолка** внутри комнаты: пол темнее базового
   цвета, потолок светлее. Мгновенно разделяет поверхности.
3. **Тёмные рёбра** через `EdgesGeometry` и `LineSegments`. Углы, косяки и кромки
   становятся видны. Работает на любом железе.
4. **Процедурная сетка на полу**: canvas 256×256 с клеткой, генерится в рантайме и
   тайлится через `repeat`. Даёт параллакс при ходьбе и ощущение масштаба.
5. **Слабый туман** `scene.fog` — глубина и мягкое сокрытие дальних границ.

Освещение: `HemisphereLight` (разная яркость сверху и снизу сама по себе разделяет
пол и потолок) плюс по одному точечному источнику на комнату с яркостью из JSON.
Тени выключены — на мобильных GPU это первое, что съедает кадр. Побочный эффект:
предметы слегка «плавают» над полом без контактной тени; при необходимости лечится
тёмным кругом-подложкой.

Четыре комнаты дают около тридцати объектов. Если карта вырастет до тридцати комнат,
статическую геометрию потребуется смерджить в один буфер; в v1 это не нужно.

### EXIT и финальный коридор

Табличка над дверью — плоскость с canvas-текстурой, на которой нарисовано «EXIT».
Материал `MeshBasicMaterial`: он не зависит от освещения, поэтому надпись остаётся
яркой даже когда мы позже погасим свет в комплексе. Рядом небольшой источник света,
чтобы табличка подсвечивала стену и была заметна через всю комнату.

Финальный коридор — обычная комната, в дальнем торце белая плоскость и сильный
источник света.

Эффект засветки при подходе делается **DOM-оверлеем**, а не bloom-постпроцессом:
белый элемент поверх канваса, прозрачность которого растёт по мере приближения к
триггеру. Bloom на мобиле дорог, здесь стоимость нулевая, а контроль полный. Этот же
оверлей плавно превращается в экран победы — один механизм на два эффекта.

## 11. Обработка ошибок

Три случая, каждый обязан давать текст, а не чёрный экран:

- **Уровень не прошёл валидацию** — полноэкранный список ошибок, игра не стартует.
  Это основной инструмент отладки карт.
- **WebGL недоступен** — внятное сообщение вместо пустоты.
- **Исключение в игровом цикле** — ловим, показываем оверлей и **останавливаем
  цикл**. Без остановки браузер получит шестьдесят одинаковых ошибок в секунду и
  вкладка ляжет.

## 12. Тестирование

Vitest, только по `core/`. Покрываем:

- валидацию уровня — каждый класс ошибки отдельным тестом;
- генерацию коллайдеров из комнат и дверей;
- разрешение движения: упор в стену, скольжение вдоль стены, поведение в углу;
- инвентарь: взять, положить, взять в руки, вернуть;
- сценарии взаимодействий целиком: подобрал ключ, взял в руки, открыл замок, дверь
  открылась, дошёл до триггера, победа;
- отказы: применение неподходящего предмета не меняет состояние.

Отдельно — тест инварианта из раздела 6: **`describe` и `apply` не расходятся.** Для
каждой пары «цель × предмет в руках» проверяется, что подсказка обещает ровно то,
что действие делает.

Рендер, ввод и UI тестами не покрываются. Проверяются руками на десктопе и
обязательно на реальном телефоне через `npm run dev -- --host`. DevTools врёт про
инерцию, мультитач и размер пальца.

## 13. Сборка и деплой

Команды:

```
npm run dev              Vite dev-сервер
npm run dev -- --host    то же, доступно с телефона по локальной сети
npm run build            продакшен-сборка в dist/
npm test                 весь Vitest
npm test <путь>          один файл тестов
```

GitHub Actions на пуш в `main`: `npm ci` -> `npm test` -> `npm run build` ->
`upload-pages-artifact` -> `deploy-pages`. Тесты идут до сборки, красные не доезжают
до продакшена. Workflow нужны права `pages: write` и `id-token: write`.

Один шаг выполняется вручную владельцем репозитория: **Settings -> Pages -> Source ->
GitHub Actions**. Без него workflow падает.

## 14. Соглашения

Хоткеи читаются **только через `event.code`** (физическая клавиша), никогда через
`event.key`. Иначе управление ломается при смене раскладки: физическая `KeyI` в
русской раскладке это «Ш», а русская «И» находится на физической `KeyB`. Инвентарь
открывается по `KeyI` и `Tab`.

## 15. Границы первой версии

**Входит в v1:** три комнаты и коридор, одна запертая дверь с замком, один ключ,
дверь EXIT с табличкой, финальный коридор с белым светом и победой. Работают ходьба,
мышь, тач, инвентарь, «предмет на предмет», подсказки и отказы.

**Сознательно не входит в v1** — не как «забыли», а как отложенное решение:

| Что | Почему отложено |
|---|---|
| Антагонист и преследование | Отдельная большая подсистема, фактически удваивает проект |
| Звук | Атмосферу даёт, но не требуется для проверки механик |
| Сохранения в localStorage | Срез проходится за минуты |
| Спринт | Добавляется за десять минут, если ходить окажется муторно |
| Тени | Первое, что съедает fps на мобильных GPU |
| Миникарта | Убивает основную механику ориентирования |
| Иконки предметов | Рисовать нечем, текст читается и на телефоне |
| Условия `requires` в правилах | Понадобятся с появлением выключателей, добавятся тремя строками |
| Процедурная генерация уровней | Требует солвера, гарантирующего достижимость ключей |
| Физдвижок | Даёт туннелирование и дрожание ради ничего |
| Текстурные файлы | Явное требование заказчика |
| Мердж статической геометрии | Нужен от нескольких десятков комнат |
