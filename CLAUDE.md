Известные и осознанно отложенные проблемы — в `known-issues.md` в корне репозитория.

Полный список того, что проверяется только глазами, — в отчётах ревью в
`.superpowers/sdd/2026-08-24-bandy-vertical-slice/`.

**Settings → Pages → Source** уже переключён на GitHub Actions, первый деплой прошёл
успешно. Если Pages когда-нибудь сбросят на ветку, прогон снова упадёт на шаге
`configure-pages` — смотреть надо туда.

**Пуш в `main` может не создать прогон вовсе.** Коммит на GitHub лежит, Actions
включены, workflow активен — а run не появляется. Дважды подряд наблюдалось во
время major outage у GitHub Actions: push-события не порождали прогонов, при том
что `workflow_dispatch` проходил. Порядок разбора, от дешёвого к дорогому:

1. Прогон вообще создался? `gh run list --limit 1` — сравнить sha с `git rev-parse HEAD`.
2. Если нет — это не workflow: `curl -s https://www.githubstatus.com/api/v2/components.json`
   и посмотреть компонент Actions.
3. Выкатить руками: `gh workflow run deploy.yml --ref main` (триггер `workflow_dispatch`
   в workflow стоит именно на этот случай).

Молчаливый неслучившийся деплой опаснее упавшего: на сайте просто остаётся старое,
и это выясняется, только когда кто-то открывает прод и не находит нового.

Проверку рендера глазами машинно сделать нельзя: под headless софтверный WebGL не
успевает отдать скриншот за таймаут, а Pointer Lock не выдаётся вовсе. Единственный
машинный способ — замер мировых координат числами; «как это выглядит» проверяет
только человек через `npm run dev`.

**Журнал работ** — что сделано, какие дефекты найдены, какие решения приняты и почему —
в `.superpowers/sdd/2026-08-24-bandy-vertical-slice/progress.md`. Это основной источник
правды о ходе работ: он переживает сжатие контекста и смену сессии, и в нём лежит
обоснование каждого решения вместе с ценой ошибки.

Каталог `.superpowers/` игнорирует сам себя правилом `*` в собственном `.gitignore` —
так устроен скилл, и ломать это не надо. Но три файла добавлены в git принудительно
(`git add -f`), потому что после выкатки они перестали быть черновиками и стали
единственной записью о том, ПОЧЕМУ код такой:

- `progress.md` — журнал работ, живой: его дописывают и дальше, правки видны в `git status`;
- `final-review-report.md` — финальное ревью всей ветки (2 Critical, 5 Important, 16 Minor);
- `re-review-report.md` — повторное ревью правок (ещё 11 находок).

Всё остальное там — брифы, отчёты исполнителей, диффы ревью — по-прежнему вне git
и восстановимо из истории. Новые файлы в этом каталоге в git сами не попадут.

Правки этих трёх файлов видны в `git status` как у любых отслеживаемых, но `git add`
по пути внутри игнорируемого каталога всё равно печатает предупреждение про
`.superpowers/sdd`. Оно безвредно — добавляй с `-f` и не удивляйся.

Задачи исполняются субагентами по скиллу `superpowers:subagent-driven-development`:
свежий исполнитель на задачу, затем независимое ревью, при находках — цикл правок.
Мелкие однотипные задачи чистой логики объединялись в один дистпетч ради экономии.

## Что это

3D-игра от первого лица в браузере. Игрок ходит по лабиринту комнат, открывает двери,
подбирает предметы, применяет предмет на предмет (ключ на замок) и ищет выход — дверь
с надписью EXIT, за которой длинный коридор с белым светом в конце.
Референс по духу — Hello Neighbor, но антагониста в первой версии нет.

Обязательное требование: играбельно и с десктопа (мышь + WASD), и с телефона (тач).

## Стек

Three.js + TypeScript + Vite, тесты на Vitest, хостинг на GitHub Pages.
Физический движок не используется: игрок — круг радиуса 0.3 в плоскости XZ,
стены — прямоугольники, движение разрешается раздельно по осям (это даёт
скольжение вдоль стены). Sweep не нужен: при 3 м/с и кадре 16 мс смещение 5 см.
Текстурных файлов нет; пространство читается за счёт цвета комнат, рёбер и
процедурных шейдеров. Надпись EXIT рисуется canvas-текстурой в рантайме.

## Команды

```
npm run dev              # Vite dev-сервер
npm run dev -- --host    # то же, но доступно с телефона по локальной сети
npm run build            # продакшен-сборка в dist/
npm test                 # tsc --noEmit, затем весь Vitest
npm test src/core/collision.test.ts   # один файл тестов
npm run typecheck        # только проверка типов
```

`npm test` намеренно начинается с `tsc --noEmit`. `vite build` типы не проверяет,
а просто срезает, поэтому без этого шага `strict` и `noUncheckedIndexedAccess`
не ловили бы ничего нигде, кроме редактора.

Отладка тач-управления делается **только на реальном телефоне** через `--host`.
DevTools врёт про инерцию, мультитач и размер пальца.

## Главное правило архитектуры

**`src/core/` не импортирует three.js. Никогда.**

Проект делится на два слоя с жёсткой границей:

- **`core/`** — чистый TypeScript: типы и валидация уровня, состояние мира
  (что заперто, что подобрано, какие флаги взведены), инвентарь, реестр
  взаимодействий, генерация коллайдеров и математика коллизий. Всё покрыто тестами,
  запускается без браузера и WebGL.
- **`render/`** — three.js: строит сцену из уровня, анимирует двери, рисует предмет
  в руках второй камерой с малым near-plane (иначе он протыкает стены).
  Читает состояние из `core`, отправляет туда команды, подписывается на события.

Между ними — **`input/`**, прячущий разницу между «pointer lock + WASD» и
«виртуальный стик + свайп» за одним интерфейсом. Остальной код не должен знать,
с какого устройства играют.

Инвентарь и HUD — **DOM-оверлей, не 3D**. Это бесплатно даёт тач-скролл, нормальные
шрифты и кнопки нужного размера под палец.

Если тянет дёрнуть меш напрямую из игровой логики — значит граница нарушается,
и это надо решать иначе.

## Взаимодействия — только данными

«Ключ на замок» — частный случай матрицы взаимодействий. Хардкод вида
`if (item === 'key' && target === 'lock')` запрещён. Правила живут в реестре:

```json
{ "use": "key_brass", "on": "lock_front",
  "effects": [{"destroy": "lock_front"}, {"consume": "key_brass"}, {"sound": "unlock"}] }
```

Добавление нового предмета должно быть правкой данных, а не кода.

## Формат уровня

Уровни пишутся руками в JSON: комнаты — прямоугольники `[x, z, w, d]` на сетке 1 м,
двери задаются парой соединяемых комнат и точкой на общей стене (ориентация выводится
автоматически). Коридор — это не отдельная сущность, а узкая комната.

Из одних и тех же данных генерируются и геометрия, и коллайдеры. Стена с дверью
режется не CSG, а тремя прямоугольниками: слева, справа и перемычка сверху.

`validateLevel()` обязана ловить опечатки автора карты (дверь ссылается на
несуществующую комнату, замок без ключа на уровне, наложение комнат) и показывать
внятные ошибки вместо запуска игры.

У замка есть ровно одно собственное свойство — название, и оно живёт в блоке
`locks` файла уровня: плоское отображение «идентификатор → строка». Замок
**описывает себя, но не называет нужный ключ**: «Железный замок», а не «Нужен:
Железный ключ». Названия предметов в этой игре и есть их типы, так что
информация у игрока та же — но сопоставляет её он, а не игра. Валидатор требует,
чтобы каждый висящий замок был назван и каждое название было использовано.

В сообщениях самого валидатора замки называются **идентификаторами**, а не
названиями: эти сообщения читает автор карты, и `lock_grate` он найдёт в JSON
поиском, а «Железный замок» — нет.

Единицы — метры. Игрок: рост 1.7, глаза 1.6, радиус капсулы 0.3. Комнаты высотой 3.0,
стены 0.2, дверной проём 0.9 × 2.1. Все константы — в `src/config.ts`.

Уровней три: `level_01` (здание), `level_02` (подвал) и `level_03` (этаж дома).
Порядок прохождения живёт в реестре `LEVELS` внутри `src/levels/index.ts`, а не в
данных уровня: валидатор видит уровень в одиночку и поле `next` внутри JSON
проверить не смог бы. Текущий уровень берётся из `location.hash`; переход на
следующий — кнопка «Дальше» на
экране победы, которая ставит хеш и перезагружает страницу, переиспользуя весь
существующий путь загрузки вместо разбора `main.ts` на переиспользуемую функцию.

`level_03` построен кольцом коридора вокруг глухой шахты — это арена для будущего
антагониста, а не украшение. **Ни одна дверь кольца (`d_ring_*`) не должна получить
замок**: замок рвёт круг и отменяет всё, ради чего уровень нарисован. Инвариант
охраняют два теста — по данным в `level_03.test.ts` и ногами, шагами по 5 см,
в `walkthrough-03.test.ts`. Замки на этом уровне висят только на комнатах,
отходящих от кольца.

**Финальный коридор обязан идти вдоль +z**, белым торцом в сторону больших z:
это требование `buildExitGlow()`, и валидатор его не проверяет. Подробности —
в `known-issues.md`.

## Жёсткие ограничения среды

- **GitHub Pages не отдаёт кастомные HTTP-заголовки** → нет COOP/COEP → нет
  `SharedArrayBuffer`. Всё, что требует потоков, использовать нельзя.
- `vite.config.ts` обязан содержать `base: '/bandy/'`, иначе на Pages белый экран
  и 404 на все ресурсы.
- ES-модули не работают по `file://`. Открывать только через dev-сервер.
- **На iPhone Safari нет Fullscreen API.** Ландшафт не залочить, адресная строка
  съедает экран. Обход — PWA (`display: standalone`).
- **Pointer Lock не существует на мобильных**, hover тоже. Подсветка цели работает
  через центральный прицел, а не через курсор.
- Мобильные GPU плохо переносят realtime-тени и большое число draw call'ов.
- После сворачивания вкладки `deltaTime` приходит в секундах и телепортирует
  игрока сквозь стены. dt всегда клампится (~50 мс), `visibilitychange` ставит паузу.

## Соглашения

- Хоткеи читаются **только через `event.code`** (физическая клавиша), никогда через
  `event.key` — иначе игра ломается при смене раскладки. Инвентарь: `KeyI` и `Tab`.
- Освещение задаётся покомнатно в JSON уровня. В первой версии свет ровный, но
  значение — множитель, чтобы позже добавить полумрак и фонарик без правки рендера.
